# Image Studio 上线检查清单（Go-Live）

## 结论先行

- 当前架构可以支撑小流量运营。
- 若目标是长期稳定运营（多人协作、可审计、可扩展），建议尽快补齐数据库与登录体系。

## 是否需要数据库

结论：建议需要，且应尽快引入。

原因：

1. 文件存储在并发、查询、审计、扩展方面会逐步成为瓶颈。
2. 兑换码、积分账本、任务状态都属于强一致业务数据，数据库更适合。
3. 后续运营报表（按日转化、渠道效果、异常统计）需要结构化查询能力。

建议最小落地范围：

1. users（用户）
2. wallets（余额）
3. credit_ledger（积分流水）
4. redemption_batches（发码批次）
5. redemption_codes（兑换码）
6. generation_jobs（生成任务）
7. admin_audit_logs（管理员操作审计）

迁移策略：

1. 先保留现有 API，不改前端交互。
2. 在服务层加 repository 抽象，先双写（文件 + 数据库）短期验证。
3. 验证后切数据库为主，文件仅作回滚兜底一段时间。

## 是否需要用户登录

结论：建议需要，但可分阶段实施。

当前状态问题：

1. 主要依赖 user_token 与 admin_token，适合 MVP，不适合长期用户体系。
2. 无法很好支持多设备、找回、封禁、风控与运营画像。

分阶段建议：

### 阶段 1（现在）

1. 保持匿名 user_token 可用，降低转化门槛。
2. 增加轻量账号体系（邮箱验证码或第三方 OAuth 二选一）。
3. 新用户默认绑定 wallet，支持匿名到正式账号合并。

### 阶段 2（增长期）

1. 引入角色与权限（admin、ops、viewer）。
2. 管理台按角色授权，敏感操作强制审计。
3. 对高风险操作增加二次确认与限流。

### 阶段 3（规模化）

1. 接入风控策略（设备指纹、IP 频控、异常兑换行为检测）。
2. 增加组织维度（团队、子账号、配额）。

## 上线前必须完成（P0）

1. 监控告警：
- 接口错误率、兑换失败率、任务失败率
- S3 上传失败告警

2. 安全与合规：
- ADMIN_TOKEN 轮换机制
- 管理员操作审计落盘
- 敏感信息脱敏（日志、返回体）

3. 数据可靠性：
- 定时备份与恢复演练
- 关键表唯一约束（兑换码哈希、流水幂等键）

4. 运维能力：
- 健康检查与就绪检查
- 灰度发布和回滚预案

## 建议近期完成（P1）

1. 管理台增加兑换批次与码列表可视化操作页。
2. 运营报表：按天兑换、补偿占比、异常码占比。
3. 更完整的自动化验收（UAT 脚本化）。

## 里程碑建议

1. M1（1-2 天）：补 P0 监控与审计最小集。
2. M2（3-5 天）：数据库接入与数据迁移。
3. M3（2-4 天）：轻量登录体系与账号绑定。
4. M4（持续）：风控与报表完善。
